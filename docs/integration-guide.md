# 프론트 연결과 검증 순서

Java 21과 PostgreSQL을 사용하는 백엔드, Node 24와 Expo/TypeScript를 사용하는 프론트는 별도 저장소다. 두 저장소를 같은 상위 폴더의 `rufit-backend`, `rufit-frontend`로 두면 프론트 통합 시험이 백엔드 JAR를 기본 경로에서 찾는다. 다른 위치라면 `RUFIT_BACKEND_JAR`로 빌드한 JAR를 지정한다.

## 전용 테스트 DB로 확인

운영·개인 기록 DB를 테스트에 연결하지 않는다. 루프백 호스트의 DB와 역할 이름은 모두 `rufit_test`이며 URL에는 쿼리나 사용자정보를 넣지 않는다. 예를 들어 포트 5435를 선택했다면 `DB_URL=jdbc:postgresql://localhost:5435/rufit_test`, `DB_USERNAME=rufit_test`와 해당 테스트 역할의 `DB_PASSWORD`를 두 저장소의 실행 환경에 설정한다. 테스트가 테이블을 정리하므로 DB를 사용하는 전체 테스트와 중단 검증을 동시에 실행하지 않는다.

| 순서 | 위치·명령 | 확인 내용 |
| --- | --- | --- |
| 1 | 백엔드 `./mvnw -B verify` | 마이그레이션, API·소유권·충돌·복구 시험, 실행 JAR와 OpenAPI 생성 |
| 2 | 프론트 `npm ci`, `npm run check` | 타입·린트·로컬 모델·통신·영속 큐 시험 |
| 3 | 프론트 `npm run test:backend` | 실제 서명 JWT·로컬 키 서버·백엔드 JAR·PostgreSQL을 연결한 기능 흐름 |
| 4 | 백엔드 `python3 scripts/smoke-restart.py` | 같은 DB를 유지한 서버 재시작과 기록 복구 |

통합 시험의 로그인 키와 계정은 시험마다 생성하는 가짜 데이터다. 외부 로그인 계정이나 앱 화면의 로그인 상태를 사용하지 않는다. 테스트 DB 주소·역할을 검사하고 자식 서버의 별도 DB 설정을 정리하여 다른 저장소로 연결되는 것을 막는다.

DB 중단·복원과 컨테이너 시험은 [백업·복구 문서](backup-restore.md) 및 [실행 이미지 문서](container-runtime.md)의 별도 조건을 먼저 확인한다. 현재 컨테이너 시험은 네이티브 Linux CI에서 검증하며, 로컬의 다른 CPU 아키텍처 에뮬레이션 환경은 동작·시간이 다를 수 있다.

## 화면 연결 시 사용할 흐름

1. 확정된 로그인 구성에서 RuFit API용으로 발급된 액세스 토큰으로 계정 세션을 만들고 `/api/v1/me`에서 검증한 ID와 서버 주소로 로컬 공간을 구분한다. 소셜 ID 토큰을 그대로 업무 API에 보내는 계약은 아니다. 실제 제공자 연결은 아직이며 [BE-02 초안과 미확정 결정](authentication-gap-analysis.md)을 먼저 확정한다.
2. 홈에서 `/workouts/active`, 주간 달력, 루틴 검색을 읽는다. 활성 운동이 있으면 그 기록을 이어간다.
3. 새 자유 운동 또는 루틴 시작 전에 작업 UUID를 보존하고 동일 작업 재시도에는 같은 `Idempotency-Key`를 사용한다.
4. 편집 중 빈 문자열은 기기에 보존한다. 유효한 세트·완료·휴식·메모를 영속 큐에 먼저 저장한 다음 `/workouts/{id}/draft`로 보낸다. 큐와 화면은 아직 연결 전이다.
5. 409 충돌은 최신 기록을 읽어 사용자에게 변경 선택을 받는다. 400/404/410으로 거절된 초안은 삭제하지 않고 확인할 수 있게 보존한다. 통신 오류·응답 유실에는 새 작업 ID로 바꾸지 않는다.
6. 미완료 세트 제외와 운동 취소·삭제에는 각각 사용자 확인을 받는다. 완료 후 결과 요약·날짜별 이력·달력을 다시 읽는다.

기본 휴식 설정은 다음 세트 완료 입력의 기본값으로 사용한다. 진행 중 휴식은 절대 종료시각을 기준으로 표시하며 화면의 초 단위 표시를 서버 저장 요청으로 만들지 않는다. 실제 회원 가입·토큰 갱신·계정 삭제·오프라인 충돌 선택 UI·실기기 검증은 [남은 범위](api-plan.md)에 명시한다.
